📊 API 아키텍처(REST, GraphQL, gRPC) 성능 벤치마킹 실험 시나리오

본 실험은 마이크로서비스 아키텍처(MSA) 환경에서 단일 데이터베이스(PostgreSQL)를 공유하는 3가지 API 패러다임의 성능과 한계를 검증하기 위해 5개의 핵심 시나리오(Experimental Units)로 구성됩니다.

🧪 실험 1. 기본 통신 및 데이터 페이로드 처리 성능 (TC 1, TC 2)

1. 목적

  • 조인(Join)이 없는 가장 단순한 단건 조회(TC 1)와 대용량 페이징 데이터 다건 조회(TC 2)를 수행하여, 통신 프로토콜별 기본 네트워크 연결 비용과 직렬화/역직렬화 오버헤드를 측정한다.

2. 기대효과(가설)

  • 페이로드가 매우 작은 단건 조회 시에는 초기 직렬화 오버헤드가 적은 REST API가 가장 낮은 지연 시간(Latency)을 보일 것이다.
  • 반면, 응답 데이터가 커지는 페이징 상황(TC 2)에서는 문자열(JSON) 기반인 REST와 GraphQL보다, 데이터를 압축 전송하는 gRPC(Protobuf)가 통신 대역폭 절약으로 인해 가장 우수한 성능을 낼 것이다.

🧪 실험 2. 구조적 한계(Under/Over-fetching) 극복 성능 (TC 3, TC 4/5)

1. 목적

  • 연관된 테이블 데이터를 조회할 때 발생하는 REST의 고질적인 약점인 N+1 호출 문제(언더페칭, TC 3)와 무거운 다중 테이블 조인 상황(오버페칭, TC 4/5)에서 각 API 아키텍처의 처리 효율을 비교한다.

2. 기대효과(가설)

  • REST API는 원하는 데이터를 조합하기 위해 네트워크 왕복(RTT)을 여러 번 거쳐야 하므로(TC 3) 응답 시간이 기하급수적으로 증가할 것이다.
  • gRPC 역시 REST와 동일하게 2번 호출해야 하지만, HTTP/2 멀티플렉싱을 통해 커넥션을 재사용하므로 REST 대비 지연 시간을 크게 단축시킬 것이다.
  • 거대한 연관 데이터를 조회할 때(TC 4/5), REST는 불필요한 필드까지 전송해 통신 병목을 유발하지만, GraphQL은 클라이언트가 명시한 필드만 추출(단 1회 호출)하여 페이로드를 최적화할 것이다. 단, GraphQL은 백엔드 리졸버의 AST(추상 구문 트리) 파싱 연산으로 인해 CPU 사용량이 높게 나타날 것이다.

🧪 실험 3. 데이터 파싱 및 예외 처리 오버헤드 (TC 6, TC 7)

1. 목적

  • 쓰기 트랜잭션(TC 6) 시 프로토콜별 역직렬화(파싱) 속도를 비교하고, 잘못된 요청(TC 7) 발생 시 서버가 예외 메시지를 규격화하여 응답하는 비용을 측정한다.
  • 클라이언트가 ID를 생성하여 전송할 때 발생할 수 있는 PK 충돌을 방지하기 위해, 모든 아키텍처는 서버에서 고유한 UUID를 생성하여 트랜잭션을 처리하도록 통일한다. 이를 통해 순수한 데이터 파싱 및 DB 쓰기 속도를 측정한다.

2. 기대효과(가설)

  • 문자열 기반의 JSON을 파싱해야 하는 REST와 GraphQL 구조보다, 바이너리 기반의 엄격한 타입을 가지는 gRPC가 데이터 매핑 및 파싱 속도에서 유리할 것이다.
  • 에러 발생 시, 텍스트 형태의 에러 객체(JSON)를 조립하는 것보다 사전 정의된 Status Code(Int)를 반환하는 gRPC의 예외 처리 지연 시간이 가장 짧을 것이다.

🧪 실험 4. 프론트엔드 연동 환경에서의 프록시 병목 분석 (TC 9)

1. 목적

  • 웹 브라우저가 gRPC-Web을 사용하기 위해 필수적인 L7 프록시(Envoy Proxy) 계층에서 발생하는 패킷 변환(HTTP/1.1 ↔ HTTP/2) 통행료(Overhead)를 집중 측정한다.

2. 기대효과(가설)

  • 순수 백엔드 간 통신인 gRPC Direct 채널에 비해, 프록시를 경유하는 gRPC Envoy 채널은 프로토콜 변환(HTTP/1.1을 HTTP/2로 업그레이드) 오버헤드로 인해 일정 수준의 지연(ms)이 발생할 것이다.
  • 특히 페이로드 크기가 기하급수적으로 커지는 대용량 조인(TC 9-2) 시, 데이터 리패킹으로 인한 지연율 격차가 더욱 벌어질 것이다.

🧪 실험 5. 극단적 트래픽 스파이크(Spike) 환경에서의 프로토콜 효율성 (TC 8)

1. 목적

  • 단 몇 초 만에 트래픽이 100배(10,000명) 폭증하는 돌발 상황을 모사하여, 각 API 통신 프로토콜(JSON 기반 vs Protobuf 기반)의 구조적 한계가 시스템 안정성에 미치는 영향을 분석한다.

2. 기대효과(가설)

  • REST/GraphQL (HTTP/1.1): 대량의 동시 연결을 맺기 위한 소켓 생성 비용과 무거운 JSON 파싱 비용이 겹치면서, CPU 스로틀링이나 커넥션 타임아웃에 가장 먼저 도달할 것이다.
  • gRPC (HTTP/2): 단일 TCP 연결을 재사용하는 멀티플렉싱(Multiplexing) 기술과 가벼운 바이너리 처리 방식 덕분에, 극단적인 스파이크 상황에서도 지연 시간 증가폭이 가장 적고 안정적으로 트래픽을 방어해 낼 것이다.
